# 踩坑清单

这份清单来自真实翻车记录。每一条都实际发生过，不是理论推演。
按「翻车代价」排序——空间和内存排在最前面，因为它们会**静默**毁掉成片。

---

## 一、空间与内存（代价最高）

### 1. 工作区快照有约 128 MB 上限，超出会静默丢弃最大的文件
不是报错，是**静默**。丢的通常正是成片（最大的那个文件）。
所以：`du -sh /home/user` 要像看仪表盘一样定期看。

### 2. `/tmp` 是 tmpfs —— 也就是内存盘
**把文件挪到 `/tmp` 不省空间，只会吃 RAM。** 这是最反直觉的一条。

实测：渲染进程已占 1.4 GB，把 46 MB 底图「移出快照区」挪到 `/tmp`，
结果是把它们从磁盘搬进了内存 → 2 GB 内存耗尽、`available` 归零、
`kswapd0` 开始颠簸 → **渲染速度掉到 1/10**（200 帧从 16 秒变成 171 秒），
还差点被 OOM 杀掉。

**省空间只有三条路：**
1. 推到 GitHub 私有仓库，验证远端完整后再删本地（推荐）
2. 压缩（见第 6 条）
3. 删掉可再生的中间产物（`chunks/`、`*.wav`、`__pycache__`）

### 3. 渲染进程常驻约 1.4 GB
6 分 48 秒的片子在 2 GB 内存的机器上，Python 进程 RSS 稳定在 1.1–1.4 GB。
**任何额外内存占用都会把它推到 OOM 边缘**：tmpfs 文件、并发的 git 克隆都算。
渲染期间不要做任何克隆或大文件搬运。

### 4. 备份/合并仓库时的内存账
190 MB 的仓库克隆到 tmpfs，就是 190 MB RAM。
要克隆大仓库做合并，先算：`空闲内存 - 克隆体积 - 1.4GB(渲染进程) > 0`。
做不到就先停掉渲染，或者接受「推上去再删本地」的单向策略。

### 5. 素材是最贵的资产，优先备份
音轨（TTS 每轮限 10 次）和底图（生图每轮限 10 次）都是**按轮限流攒出来的**，
重做代价远高于成片。它们一准备好就该推私有仓库。

### 6. 压缩手法
- 底图转自适应调色板 PNG（200 色）：省 26–37%，视觉无损
- 音轨用 mp3 不用 wav：6.8 分钟立体声 wav 有 **70 MB**，mp3 只有 7.8 MB
- 拼音轨后立刻删 wav

## 二、Git / GitHub

### 7. force push **不会**删除已泄露的文件
`git reset --hard <old>` + `push --force` 之后，旧 SHA 的孤儿对象
**仍然可以通过 raw URL 访问**。实测：`吃辣.mp4` 25 MB 在 force push 后仍能 200 下载。
唯一能销毁它们的办法是**删除仓库再重建**。

### 8. 删仓重建后，CDN 缓存仍会返回 200
`raw.githubusercontent.com` 的缓存不受仓库重建影响，
`?cb=` / `?raw=1` 等查询串**绕不过去**。需要联系 GitHub Support 清缓存。
**凡是推到公开仓库过的东西，永远假设它还在外面。**

### 9. `api.github.com` 匿名访问会 403（限流）
验证文件是否存在，用 raw URL + HTTP 状态码，或者带 token 调 API。
不要因为 403 就以为文件不存在。

### 10. `.gitignore` 里的 `*.mp4` 会静默吞掉成片
`git add -A` 直接跳过它，`push` 显示成功，但成片根本不在仓库里。
**推完必须核对**：`git -c core.quotePath=false ls-files | grep '\.mp4$'`，
必要时 `git add -f`。

### 11. 中文路径下 `!examples/**/*.mp4` 这种否定规则无效
改成目录级 `!examples/`，或直接 `git add -f`。

### 12. `git ls-files` 对非 ASCII 路径做八进制转义并加引号
输出是 `"docs/\346\240\267\345\274\240.png"` 这种形式，
导致 `grep '\.mp4$'` 匹配不到——**末尾多了个引号**。

必须用 `git -c core.quotePath=false ls-files`。

实测翻车：合并仓库后统计「mp4/mp3/png 各多少个」，四个计数全是 0，
但文件总数 131 = 62+69 精确吻合。数字自相矛盾时**先怀疑检查命令**，
不要据此判定素材丢失。我差点中止整个合并。

### 13. 新建仓库默认分支可能是 master
推送前 `git branch -M main`，否则 clone 下来对不上。

### 14. PAT 不要写进 remote URL
用 extraheader 传：
```bash
B64=$(printf 'user:ghp_xxx' | base64 -w0)
git -c "http.https://github.com/.extraheader=AUTHORIZATION: basic $B64" push
```
用完后提醒用户去吊销。

### 15. 删仓前先独立验证
从远端**重新克隆一份**比对文件数和关键文件字节数，通过了再删旧仓库。
不要拿本地暂存区的状态当远端状态。

## 三、生成额度

### 16. `generate_image` 和 `generate_speech` 各自每轮硬上限 10 次
每收到一条新用户消息重置。**同一条消息里交错调用不会提高任何一边的上限。**
按 ≤10/轮 规划：46 张底图 = 5 轮，23 段 TTS = 3 轮。

### 17. `voice_id` 是会话局部的
跨会话失效，不要写进文档当成固定值。

## 四、TTS

### 18. 音色必须可复现
不能只依赖 `voice-00`。要留下：固定试音文本 + 参数 + 实测声学指标
（电平 dB、时长）+ 参考音频，并且**让用户听确认过**再开始合成全片。

### 19. 参考文本可能有直引号 `"` 而原文是弯引号 “ ”
逐字校验前先规范参考文本。否则字符数能对上，但引号是错的。

### 20. 同样的文本+音色可能得到完全相同的音频
想换语调时，重复调用是浪费额度。有效做法是**改变从句边界**拆分合成，
再拼接——把问题词放在新片段的开头，韵律会重新起头。

### 21. TTS 会在特定词上读错声调
（实测「脑子」被读错）。逐字不改的稿子不能改词，
只能换切分位置重生成，让用户听选，再把选中的片段拼回去。

## 五、代码复用

### 22. 复制 `weight()` / `build_timeline()` 时必须连常量一起复制
它们引用 `_PUNCT_HEAVY` / `_PUNCT_LIGHT`，这两个定义在函数**之前**。
只抄函数会 `NameError`。

### 23. 路径布局约定曾自相矛盾
`build_audio.py` 的 `AUDIO` 按「脚本在 `scripts/` 子目录」写，
`compose.py` 的 `ART` 按「脚本在根目录」写。平铺布局必崩。
已改为自动探测两种布局（见 `_find()`）。

### 24. `TITLE_LINES` 注释在撒谎
注释写「留空则不显示」，代码却在空列表时执行 `TITLE_LINES[-1]` → `IndexError`。
**任何人拿本 skill 开新项目、不填片名就会崩。** 已补守卫。

### 25. 反向切片 + `s.replace("", new)` 会在每个字符间插入内容
实测 900 行 → 238 万行 / 100 MB。
**替换前一律 `assert count(old) == 1`，全部替换成功后再写盘。**

### 26. Python 包不跨会话保留
每会话重装：`numpy pillow imageio_ffmpeg scipy`。

### 27. 裸 `ffmpeg` 不在 PATH
用 `imageio_ffmpeg.get_ffmpeg_exe()`。

### 28. 读图没有视觉，只有数字
`read_file` 读 PNG 返回的是「[An image was provided here…]」。
所有图片验收都得靠数值指标（底色偏离、墨量占比、包围盒）。

## 六、渲染

### 29. 单趟全片渲染会 BrokenPipe 挂掉（约 512 帧）
必须用 `render_chunked()`（`render()` 内部已调用它）。

### 30. 逐帧大半径 GaussianBlur 是 1.28 s/帧
静态图层必须预烘焙一次，不能逐帧算。

### 31. `compose.py test` 只出视频不出音频
需要单独混流。

### 32. `compose.py` 不支持 `--help`
传了 `--help` 会被当成未知参数忽略，然后**直接开渲**。
看用法去读 `__main__` 那段。

### 33. 渲染中途会变慢十倍 —— 先查内存不是磁盘
见第 2 条。磁盘 20 G 可用时照样卡，因为是内存颠簸。

## 七、运镜与画面

### 34. `ken_burns` 的 `px/py` 是「可取景范围」的比例，0.5 = 居中
`ZMIN` 必须 ≥ 1.05。

### 35. 整块主体的呼吸缩放和旋转会被看成悬浮贴纸
`FG_SCALE` / `FG_ROT` 已弃用。要的是**零件逐个揭示**（依次滑入淡入后静止）
+ 关键镜头的**多状态帧**。

### 36. 不要横向运镜
横摇（px 大范围 sweep）和手持漂移（dx/dy 正弦）叠加起来会被读成「晃动」。
纯推近最稳。不截断由 `z_fit` 钳制 + `Plate.frame()` 取景钳制保证。

### 37. 状态帧提示词必须禁止重画
写清楚 "CRITICAL: geometry is locked... Only fill colours may change"。
否则模型会重排构图，溶解时就会跳。

### 38. 状态帧验收不要用包围盒位移
淡色小元素（虚线、浅色点缀）在墨量阈值边缘跳变，会把包围盒拽飞。
实测误报 210px，但直接对比两图包围盒完全相同。

改用「变化像素落在主体包围盒内的比例」：
- 差异占比 0.15% ~ 30%
- 变化像素 ≥90% 落在主体包围盒内
- 两条同时满足才算合格

## 八、字幕与排版

### 39. 字幕必须与插画物理隔离
独占底部色带（如 `ART_H=900` / `BAR_TOP=900` / `BAR_H=180`），
两区不重叠，字幕永远压不到画。验收时抽帧分别统计两区的墨量。

### 40. 镜头时长要均衡
按字数权重自动分配会出现 1.4 秒和 19 秒的极端值。
重新分配字幕行可以拉平到 3.6–12.7 秒（中位 8.9 秒）。
单镜短于 2.5 秒，零件揭示动画还没播完就切了。

## 九、命令行与脚本细节

### 41. `build_audio.py` 会留下 `seg*.wav` 且不清理
它把每个 mp3 转成 wav 再拼接，拼完**不删**。
23 段片子实测残留 **69 MB**，而 mp3 原文件只有 15 MB。
拼音轨后必须 `find audio -name '*.wav' -delete`。

### 42. `while read` 会吃掉末尾没有换行符的最后一行
```bash
printf '%s\n' "$A" > list.txt      # 有换行，安全
python3 -c "print('\n'.join(names))" > list.txt   # 末尾无换行 → 最后一项被跳过
```
实测：批量下载 57 张底图，只下回来 56 张，漏的正是列表最后一项。
`while read -r x || [ -n "$x" ]` 才能兜住，或者干脆用 `printf '%s\n'` 生成列表。

### 43. ffmpeg concat 解复用器按「列表文件所在目录」解析相对路径
不是当前工作目录。列表写 `file 'a.mp3'` 而列表在 `/tmp`，就会去找 `/tmp/a.mp3`。
**列表里一律写绝对路径。**

### 44. `ffmpeg -v error` 会把 `volumedetect` / `silencedetect` 的输出一起屏蔽
这两个滤镜走 stderr 的 info 级。加了 `-v error` 就什么都不输出，
看起来像命令失败了。**测音量/测静音时不要加 `-v error`。**

### 45. 改一段音频，就得重拼整条音轨
分段音轨（seg01…segNN）是音轨的**源**，不是中间产物。
删了它们，改任何一个片段都无法重建全片。
实测：为腾空间把 seg*.mp3 移走并删除，之后改结尾一句时
只能从 GitHub 逐文件拉回 22 段。**分段音轨要么留着，要么确保仓库里有。**

### 46. 改了音频，必须同步 `script.py` 里硬编码的 `dur`
分镜时间轴按每段 `{"dur": X.XX}` 分配镜头时长。
音频换了而 `dur` 没更新，字幕就会和口型错位。
改完音频后重跑一遍实测并重写全部 `dur`（不要只改那一段，顺带校准全部）。

## 十、续渲与中断

### 47. `render_chunked` 的续渲检查会放过被截断的残片
它判断「分片已存在」只看 `os.path.getsize(part) > 100000`（100 KB）。
进程被 SIGKILL 时正在写的分片有 **3.1 MB**，轻松通过检查 →
**一个只写了一半的分片会被当成完整的接进成片**，成片在中间断掉。

续渲前必须逐片测时长，删掉明显偏短的：
```bash
for f in chunks/c*.mp4; do ffprobe -i "$f" 2>&1 | grep Duration; done
```
实测：完整分片 38–48 秒，残片只有 28 秒（应 41.7 秒）。

### 48. OOM 被杀不会有任何报错，只有一行 `Killed`
exit code 137 = SIGKILL。日志停在中途，没有 traceback。
长片渲染时要盯 `free -m` 的 available，低于 100 MB 就危险。

### 49. 续渲很便宜，不要从头再来
`render_chunked` 会跳过已完成的分片。
实测：11 段里 9 段已存在时，补完剩下的只花 **98 秒**（全片需 15 分钟）。
被杀之后第一反应应该是「删掉残片 → 原样重跑」，不是删掉重渲。

### 50. 别在渲染期间跑 git 克隆/推送
这条在第 3 条已经写过，但还是犯了一次：
渲染进行到一半时并行推了 skill 仓库，内存从够用直接归零，进程被 OOM 杀死。
**渲染期间，除了轮询进程状态，什么都不要做。**


## 十一、线粒体项目新增规则（51–61）

详见 [音色-变速-多图-双端备份](音色-变速-多图-双端备份.md)。

51. 相同音色 index 不保证复现；选中的 ID 不等于现有音轨 ID，必须分别记录。
52. 1.25倍速必须在重建时间轴前完成，使用atempo保音高，原速分段不覆盖。
53. 变速后测每段真实时长，更新镜头与SRT；字符权重不是强制对齐。
54. 8张底图切50次仍是8张图；用户要求多图时按机制补独立素材。
55. 本环境实测单轮生图10次，并行也不能突破；失败项不得计入完成数量。
56. 128MB是快照尽力上限，不是可用磁盘；临时克隆和传输包不要挤占持久化预算。
57. 素材默认私有GitHub；Skill可更新原仓库；不要误把私有素材放公开Skill。
58. 双端备份需独立校验：GitHub重新克隆核对文件哈希，MCP校验归档及逐文件哈希。
59. MCP命令可能成功却返回空输出，改写日志再read_files；新增文件前确认父目录存在。
60. PAT不进代码/日志/归档/远端URL，用后清除临时凭据并提醒撤销；旧成片、现行音轨和新选择分别标记。

61. 新建临时隧道在MCP侧可能尚不能解析。核实A记录后仅对该curl调用用--resolve，保留HTTPS证书校验，勿使用-k或改全局DNS。


## 十二、图片密度与真实自检（62–68）

详见 [密度-语速-音画对齐-验收规范](密度-语速-音画对齐-验收规范.md)。

62. 图片密度同时统计独立图、实际镜头和每分钟图数；8–12张/分钟为默认目标，工作版至少6张/分钟。
63. 1.25倍只是用户倍率，不是固定字数/分钟；变速后重新测时长，术语可懂度仍需检查。
64. 独立ASR逐段比对、保留差异和试听片段；同音字常是假阳性，不把识别结果当发音认证。
65. 台词按时长均分会导致图讲错机制：必须逐镜用原文短语切点和对应机制图重新编排。
66. ASR词时间戳可单调匹配原文字符，其余插值；记录锚点覆盖率，不能谎称强制对齐误差已经实测。
67. 多图渲染改为每镜FFmpeg独立进程可控制内存；全部成片解码、核对帧数、每镜抽帧和响度，不只打开播放器。
68. 缓存标识必须包含时间轴、音轨、代码、图片哈希；修改素材后不能直接复用旧分片。工作版和终审合格版本必须明确区分。

69. 重复备份时暂存目录可能残留上轮SHA清单；生成新清单时必须显式排除清单自身，否则会把旧清单哈希写进去，新克隆自检必失败。修正后重新推送并再次独立克隆，不能忽略失败项。

70. MCP已有同名Skill可能来自不相关Git历史。快进合并失败后不要force/reset；保留原目录，在独立的最新版目录克隆并校验。
71. 复合Shell命令的最后一个命令成功会掩盖前面的失败；用set -e或&&串联关键步骤，并检查日志里的fatal/error，不能只看run_command外层exit_code。

72. Windows新克隆可能因autocrlf把所有文本换成CRLF，导致同一提交SHA正确但逐文件哈希不一致。先检查差异是否仅换行；用仓库.gitattributes显式固定文本LF、媒体binary，或对新建无用户改动的克隆禁用autocrlf后重新检出。不得把换行差异误报为媒体损坏，也不能跳过哈希检查。


## 十三、结尾「脑子」与速度变更（73–76）

73. 固定结尾「脑子」被用户重复指出错读，即使ASR识别正确也不能忽略；脑nǎo第三声、子轻声，每次改声线/速度后重新回听。
74. 不把固定结尾塞在长语段最后；优先独立合成问题词开头的短句，保留原词、原速及试听版本。
75. 1.25改为1.2要从原速新片段重做atempo，实测时长、重建字幕和镜头，不能只改文件名或播放器速度。
76. 多视频封面需要先查明主题来源；封面背景占用图片额度。四封面加六分镜是一轮10次，不能虚报十张分镜完成。
